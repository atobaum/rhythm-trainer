# 타이밍 판정

## 1. 배경

배경은 [[design#1. 배경]]과 같다. 이 기능 고유의 맥락은 브라우저에서 오디오 시계와 입력 시계가 다르고, 기기마다 터치 입력 지연과 오디오 출력 지연이 다르다는 점이다. 판정을 믿을 수 없으면 다른 기능이 다 있어도 제품을 쓸 이유가 없다.

## 2. 목표

- 사용자의 각 탭이 어느 음표에 대응하는지, 몇 ms 빠르거나 늦었는지 판정된다.
- 놓친 음표(Miss)와 불필요한 탭(Extra)이 따로 집계된다.
- 같은 입력 데이터에는 항상 같은 판정이 나온다.
- 실기기 측정으로 웹 유지 여부를 판단할 근거(지연, 지터)가 나온다.

## 3. 비목표

- 기기 간 절대 정확도. 같은 기기에서의 일관성까지만 보장한다.
- 블루투스 이어폰 지연 보정. 기준 환경은 내장 스피커다.
- 강세 판정. 터치로 측정할 수 없다.

### 실패로 볼 것

- 음표 하나를 놓쳤더니 이후 탭이 전부 한 칸씩 밀려 판정된다.
- 연속 두 탭이 같은 음표에 둘 다 매칭된다.
- 정확히 쳤다고 느끼는데 매번 다른 판정이 나온다(지터가 판정 범위를 넘음).

## 4. 사용자 흐름

1. 연습 시작 시 오디오 시계와 입력 시계의 대응 관계를 기록한다.
2. 연주 중 탭마다 타임스탬프를 기록하고 즉시 화면에 넘긴다([[practice-screen]]).
3. 매칭이 확정될 때마다 판정 결과를 넘긴다.
4. 연습이 끝나면 지표를 계산한다.

## 5. 기능 정의

### 입력 시간

- 오디오는 `AudioContext.currentTime` 기준으로 예약 재생한다.
- 탭 시각은 `PointerEvent.timeStamp`(pointerdown)를 쓴다. 콜백 실행 시각을 쓰지 않는다.
- 두 시계는 직접 비교하지 않고, 시작 시점의 대응 관계로 변환한다.
- `pointerId` 로 중복 입력을 막는다. pointerdown 한 번이 입력 하나다.

### 매칭

시간 순서를 보존하는 일대일 매칭. 입력 하나는 목표 하나에만, 목표 하나는 입력 하나에만 매칭된다. 허용 범위 W 밖은 매칭하지 않는다. 손(트랙)이 다르면 따로 매칭한다.

동적 계획법 시퀀스 정렬로 총비용 최소를 찾는다. 동점이면 오차가 작은 쪽을 우선한다.

```
C_match(i, j) = |u_j - e_i| / W   if |u_j - e_i| <= W, else infinity
C_miss = 1
C_extra = 1
```

### 판정 범위 (설정값, 초기 가설)

| 절대 오차 | 판정 |
|---|---|
| ≤ 30ms | Perfect |
| ≤ 70ms | Great |
| ≤ 120ms | Good |
| > 120ms | Miss / Extra |

방향 구분 입력(기타 스트로크)에서 타이밍은 맞고 방향이 틀리면 `wrong-direction`.

### 지표

| 지표 | 정의 |
|---|---|
| Hit Rate | 매칭된 목표 / 전체 목표 × 100 |
| MAE | 매칭된 입력의 평균 절대 오차 |
| 평균 부호 오차 | 매칭된 입력의 (탭 − 목표) 평균. 양수면 늦는 경향 |
| Miss Count | 매칭 안 된 목표 수 |
| Extra Count | 매칭 안 된 입력 수 |

MAE 는 놓친 음표를 빼고 계산하므로 Hit Rate, Miss, Extra 를 항상 같이 보여준다. 종합 점수는 단순 가중합이고 개별 지표를 같이 보여준다.

### 탈락한 후보

| 후보 | 탈락 사유 |
|---|---|
| 각 탭을 가장 가까운 목표에 붙이기 | 두 탭이 한 목표에 붙고, 누락 후 이후 매칭이 밀림 |
| 탭 횟수만 세기 | 놓친 것과 엉뚱한 타이밍을 구별 못 함 |
| 콜백에서 `performance.now()` 로 탭 시각 기록 | 메인 스레드 지연이 그대로 오차가 됨 |
| 메인 스레드 타이머(setTimeout)로 소리 재생 | 재생 시각 자체가 흔들림 |

## 6. 설계

### 데이터

| 개념 | 담는 것 |
|---|---|
| 입력 | 타임스탬프(ms), 트랙, 입력 수단(터치, 마우스, 키보드), 방향(스트로크) |
| 목표 이벤트 | 원본 패턴 이벤트, 트랙, 목표 시각(ms), 방향 |
| 판정 | 목표 이벤트, 입력(둘 중 하나는 없을 수 있음), 결과, 오차(ms) |
| 연습 결과 | 문제, 시작·종료 시각, 판정 목록, 지표 5개 |

- 매칭·판정·지표는 `src/domain/evaluation/` 의 순수 함수. 시계와 입력 수집은 `src/infrastructure/` 가 맡는다.
- 브라우저가 백그라운드로 가면 오디오와 판정을 멈추고 세션을 미완료로 처리한다.

### 웹 vs 네이티브 판단

| 지연 | 브라우저 | 네이티브 |
|---|---|---|
| 터치 이벤트 전달 | 브라우저 처리 경로를 거침 | OS 입력 이벤트에 더 직접 접근 |
| 오디오 출력 | Web Audio 로 정밀 예약 가능 | Core Audio, Oboe/AAudio 로 더 세밀 |
| 화면 표시 | 렌더링 프레임 영향 | 더 세밀하지만 디스플레이 지연은 남음 |

일정한 지연은 보정할 수 있고, 탭마다 흔들리는 지터는 보정할 수 없다. 판단 기준은 지터다. 실기기에서 지터가 Perfect 범위(±30ms)를 흔들 만큼 크면 네이티브를 검토한다. Flutter 도 일반 터치 이벤트와 오디오 플러그인만으로는 저지연이 보장되지 않는다.

## 9. 열린 문제

- 판정 범위를 BPM 에 따라 바꿀지(빠른 템포에서 W 가 음표 간격보다 커지는 문제)
- 측정 모드를 사용자 기능으로 노출할지, 개발용으로만 둘지
- 기기별 고정 지연 보정값을 자동 측정할지, 수동 설정할지
