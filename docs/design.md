# Rhythm Lab 설계

프로젝트 전체의 배경과 목표, 비목표, 설계 원칙을 기록한다. 기능 문서(`docs/features/`)는 이 문서를 전제로 쓴다. 사용법은 `README.md` 에, 근거는 여기에.

## 1. 배경

- 기타를 연습하는데 리듬을 맞추기 어렵다. 특히 쉼표, 싱코페이션, 다운·업 스트로크 패턴에서 박자를 놓친다.
- 메트로놈은 일정한 박자를 들려줄 뿐, 내가 리듬 패턴을 맞게 치는지, 얼마나 빠르거나 늦은지 알려주지 않는다.
- 반복 연습해도 어떤 부분을 어떻게 틀렸는지 구체적으로 알기 어렵다.

## 2. 목표

- 사용자는 홈에서 시작 버튼 한 번으로, 설정 없이 지금 실력에 맞게 구성된 연습을 시작할 수 있다.
- 사용자는 화면의 악보를 보고 카운트인 후 화면을 탭해 리듬을 연주하고, 각 탭이 목표보다 얼마나 빠르거나 늦은지를 탭하는 즉시 볼 수 있다.
- 사용자는 리듬을 먼저 듣고 기억한 뒤 악보 없이 탭으로 재현할 수 있다.
- 사용자는 연습이 끝나면 놓친 음표, 불필요한 탭, 평균 오차, 빠르거나 늦게 치는 경향을 확인할 수 있다.
- 사용자는 커리큘럼(4분 → 8분 → 16분음표와 쉼표)을 단계별로 진행하고, 앱을 다시 열면 지난번 진도와 틀린 리듬 복습부터 이어갈 수 있다.
- 같은 기기에서 같은 연주를 반복하면 판정 결과가 일관되다. 실제 iPhone·Android 기기에서 측정한 탭 지터가 Perfect 판정 범위(±30ms)를 흔들지 않는다.

## 3. 비목표

- 메트로놈 앱. 박자 기준음은 리듬 연습의 보조로만 제공하고, 메트로놈 단독 기능(탭 템포, 다양한 박 소리 프리셋 등)은 만들지 않는다. 이유는 이미 무료 앱이 많고 이 프로젝트의 문제와 무관해서다.
- 낙하 노트형 리듬 게임. 움직이는 물체에 반응하는 능력과 스스로 박자를 예측하고 유지하는 능력은 다르다.
- 계정, 서버 동기화, 소셜, 랭킹, 결제. 개인용으로 시작하고, 넣으면 백엔드 운영이 생긴다.
- 실제 기타 소리(마이크) 인식, MIDI 기기 입력. 신호 처리가 별도 프로젝트 규모다.
- 터치 압력으로 강세 판정. 터치 압력은 실제 스트로크 강세와 대응하지 않는다.
- AI·LLM 기반 코칭과 문제 추천. 규칙 기반으로 충분하고, 근거 없는 피드백을 만들 위험이 있다.
- 기존 앱의 콘텐츠·UI 복제. 학습 구조만 참고한다.
- 절대적인 음악적 타이밍 측정기. 기기마다 입력·출력 지연이 다르므로, 같은 기기에서의 일관성까지만 보장한다.

### 실패로 볼 것

- 판정이 같은 연주에 대해 들쭉날쭉해서 결과를 믿을 수 없다.
- 시작 버튼을 눌렀는데 너무 쉽거나 어려운 문제만 나오거나, 같은 문제만 반복돼서 결국 직접 고르게 된다.
- 연습 중 피드백이 연주를 방해해서 리듬에 집중할 수 없다.
- 같은 패턴을 외워서 점수가 오를 뿐, 처음 보는 같은 난이도 패턴의 정확도는 그대로다.
- 모바일에서 탭이 스크롤·확대 같은 브라우저 제스처로 먹힌다.

## 4. 사용자와 사용 상황

- 사용자는 본인 1명. 기타 초급~중급, 악보는 기초 수준으로 읽는다.
- 주로 스마트폰으로, 기타 연습 전후나 짬날 때 3~15분 연습한다. 악기 없이 화면만 탭한다.
- 기기 내장 스피커를 기준으로 한다. 블루투스 이어폰은 출력 지연이 커서 판정 기준 환경에서 제외한다.
- 네트워크가 없어도 연습할 수 있어야 한다. 최초 설치 후 오프라인 동작.
- 데이터는 그 기기의 브라우저 저장소에만 있다.

## 5. 설계 원칙

- 리듬 하나는 하나의 데이터 모델로 표현한다. 악보 렌더링, 오디오 재생, 탭 판정, 청음, 양손, 폴리리듬, 스트로크가 같은 데이터를 쓴다.
- 판정 엔진(`src/domain/`)은 React, Web Audio API, VexFlow 에 의존하지 않는 순수 함수로 만든다. 같은 입력이면 항상 같은 결과다. 네이티브로 옮겨도 그대로 쓸 수 있다.
- 시간은 오디오 시계와 이벤트 타임스탬프로 계산한다. 메인 스레드 타이머로 재생하거나 콜백 실행 시각을 탭 시각으로 쓰지 않는다.
- 피드백은 측정 결과에 근거할 때만 준다. 원인 추정은 여러 번 관찰해 근거가 충분할 때만 보여준다.
- 사용자에게 고르게 하지 않는다. 기본값으로 바로 시작하고, 고르고 싶을 때만 커리큘럼·자유 연습·설정으로 간다.
- 임계값(판정 범위, 템포 조정 조건, 큐레이션 비율)은 코드에 박지 않고 설정값으로 둔다. 전부 가설이고 측정 후 조정한다.
- MVP 범위는 좁게, 데이터 모델은 넓게. 다중 트랙과 유리수 위치는 처음부터 지원해 양손·폴리리듬을 추가할 때 엔진을 다시 쓰지 않는다.

순서 1~6이 MVP 다. 7 이후는 MVP 이후다.

| 순서 | 기능 | 한 줄 설명 | 문서 | 상태 |
|---|---|---|---|---|
| 1 | 리듬 엔진 | 유리수 기반 리듬 모델과 목표 이벤트 생성 | [[rhythm-engine]] | done |
| 2 | 타이밍 판정 | 시계 동기화, 이벤트 매칭, 판정, 지표 | [[timing-judgement]] | implementing |
| 3 | 읽기·모방 연습 | 악보 보고 치기, 듣고 따라 치기와 공통 연습 상태 | [[reading-imitation]] | implementing |
| 4 | 연습 화면·실시간 피드백 | 악보, 타이밍 트랙, 탭 영역, 자동 템포, 결과 화면 | [[practice-screen]] | implementing |
| 5 | 커리큘럼·자유 연습 | 음형별 110단계와 진도, 도입 마디와 매번 새로 만드는 마디 흐름, 고정·스트로크·양손·폴리리듬 목록 | [[curriculum]] | done |
| 6 | 빠른 연습 | 원탭 시작, 연습 시간 설정, 자동 큐레이션 | [[quick-practice]] | done |
| 7 | 리듬 청음 | 듣고 악보 고르기·완성하기 | [[dictation]] | done |
| 8 | 기타 스트로크 | 다운·업·헛스트로크 패턴 | [[guitar-strumming]] | done |
| 9 | 양손 독립 | 좌우 탭으로 서로 다른 리듬 | [[two-hand]] | implementing |
| 10 | 폴리리듬 | 2:3, 3:4, 4:5, 직접 지정 | [[polyrhythm]] | done |
| 11 | 노래에 맞춰 치기 | 저작권이 끝난 노래 멜로디를 들으며 그 리듬을 끝까지 치기 | [[songs]] | implementing |

가장 먼저 만들 것은 4/4 악보 표시 → 카운트인 → 화면 탭 → 오차 판정 → 결과 확인의 수직 슬라이스다(1~4). 4의 실기기 측정 결과로 웹 유지 여부를 판단한다.

## 8. 열린 문제

- 판정 범위(Perfect ±30, Great ±70, Good ±120ms)와 자동 템포 조건(3연속 성공 +5, 2연속 실패 −5 BPM)의 실제 값
- 성공·실패를 Hit Rate, MAE, Miss, Extra 로 어떻게 합산할지
- 상태 관리 라이브러리, 배포 위치

### 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| 모바일 입력 지연·지터 | 판정 불신 | 시계 동기화, 실기기 측정, 필요하면 네이티브 |
| 오디오 출력 지연 | 기준음보다 늦게 반응 | 출력 지연 측정 및 보정 |
| 백그라운드 전환 | 오디오·타이머 불안정 | 세션 자동 정지 |
| 복잡한 악보 렌더링 | UI 오류 | VexFlow 지원 범위 선검증 |
| 패턴 자동 생성 오류 | 학습 품질 저하 | 생성 패턴 유효성 검사 |
| 작은 화면 | 악보 가독성 | 마디 단위 레이아웃 |
| 기기별 멀티터치 차이 | 양손 훈련 오류 | 실기기 테스트 |
